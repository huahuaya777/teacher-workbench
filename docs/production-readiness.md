## 已写入项目、尚未在服务器运行

- `compose.production.yaml` 使用独立项目名 `teacher-workbench-production` 和独立数据库、Redis、私有文件、静态资源卷；与现有 `teacher-workbench-test` 测试栈分开。网关只绑定 Ubuntu 回环地址 `127.0.0.1:18080`，不会直接监听局域网或公网。
- Web 使用 Gunicorn；静态文件由单独 Nginx 网关从只读静态卷提供；私有上传卷只给 Web/worker，网关不能直接读取。数据库迁移**不会**随容器启动自动执行，正式升级前需先做数据库与文件配对备份并演练回退。
- 首轮草案强制 `AI_ENABLED=0`、空 `AI_API_KEY`。这避免未建立个人密钥与额度控制时静默产生付费调用；也意味着此草案还不能用于真实 AI 作业生成。
- `scripts/check_production_env.py` 检查独立密钥、数据库密码、真实域名、HTTPS 来源、关闭调试、关闭 AI 等字段，不输出密钥值。它只检查配置文本，不能代替现场 HTTPS、登录限速或恢复演练。
- **2026-10-17 本机修正：**复核用户当前 EasyTier 私网 IP 配置时，发现原 `valid_hostname()` 会误把 `10.0.30.5` 当成域名格式通过；已使用 Python 标准库 IP 地址解析明确拒绝 IPv4/IPv6 字面量。3 项针对性回归、Python 编译和一组虚构 IP/HTTP 配置拒绝检查均通过。这个修正只在本地，Ubuntu 运行栈未更新；真实域名和可信 HTTPS 的现场闸门仍必须分别核验。
- 普通登录页与 Django 管理员登录页已在本地共用用户名维度的错误密码限制：15 分钟窗口内 8 次失败后返回 HTTP 429；成功登录清除该用户名的错误计数。计数键是加密摘要，不含明文用户名。正式配置使用共享 Redis 缓存，Redis 不可用时不会退回每进程内存。Ubuntu 一次性容器的 PostgreSQL 回归与两个进程共享虚构 Redis 键已由用户现场输出证实；独立预发布栈的真实 HTTP 限速探针及虚构普通账号浏览器登录已通过，旧测试栈仍用旧代码，正式入口尚未验收。当前内网穿透尚未证明可提供可信客户端 IP，所以暂不依据 IP 分组；针对用户名的恶意锁定、批量随机用户名和 Redis 故障仍是需监测的边界。
- `config/nginx-production.conf` 会把上游请求标记为 HTTPS。因此**只有经现场确认的可信 HTTPS 入口能够独占连接回环 18080 端口**时才能使用。用户现有 EasyTier 在 PVE LXC 140 提供私网可达路径，不处理工作台网页的 HTTPS；入口应在 Ubuntu 257 上单独配置并核对无 HTTP 绕过，见[网络访问计划](network-access-plan.md)。
- 2026-10-17 用户只读监听结果显示 Ubuntu 80/443/18080 当时无监听，测试站仅绑定回环 18000；这为未来独立入口保留了端口选择，但不证明防火墙放行或远程可达。助手的候选域名只读 DNS 查询曾返回公网 AAAA；用户现已明确暂不使用该域名，Cloudflare 核对和 HTTPS 配置均留待以后。**现有正式 Compose 草案强制 HTTPS，不能直接改成 HTTP 在 EasyTier 中当正式站运行。**

## 发布前必须逐项取得证据

**2026-10-17 当前进度：**独立 `compose.staging.yaml` 与离线包已在 Ubuntu 启动；用户返回新站 HTTP 登录限速、Nginx 静态资源技术探针及旧站登录页仍可用的成功标记。用户随后在临时隧道浏览器以虚构普通账号进入预发布首页，并确认虚构 DOCX 上传下载打开正常；助手复核带 Origin 的虚构错误登录 POST 返回 HTTP 200。原测试站继续使用旧代码。预发布通过不能代替可信 HTTPS、凭据恢复或正式发布批准。

**预发布发现并复核的问题：**浏览器在本地隧道 `:18002` 登录时，Django 曾因 Origin 带端口而 Nginx 转发 Host 丢端口返回 403。虚构 POST 复现后，本地预发布 Nginx 改为转发原始 `$http_host`；之后用户成功登录，助手的带 Origin 虚构 POST 返回正常登录提示。用户未提供网关热重载脚本终端输出，不能把脚本内部检查逐项标为已见证。正式草案当前按标准 HTTPS 域名设计，尚未做实际入口的 CSRF 验收；未来发布前须用实际域名/端口实测登录，不得沿用预发布技术探针当作正式登录证明。

1. **HTTPS 与入口（用户当前暂缓）：**EasyTier 产品与 LXC 140 配置已由用户提供；先只读核对家外客户端到 Ubuntu 的路由。待用户以后恢复域名/HTTPS 计划时，再确认实际域名、证书、强制 HTTPS、转发目标及是否存在可绕过 TLS 的 HTTP 路径；核对 `X-Forwarded-Proto` 由本项目网关覆盖，外部客户端不能自行伪造。之后才可在服务器私有 `.env.production` 中将 `TW_HTTPS_INGRESS_VERIFIED=1`。这个字段只是操作记录，不能证明网络真的安全。
2. **账号与访问：**登录限速本机假账号测试、Ubuntu 一次性 PostgreSQL 回归、虚构 Redis 键跨进程共享及独立预发布栈的真实 HTTP 共用失败计数探针已通过；虚构普通账号已能浏览器登录。15 分钟自然恢复、普通账号对管理页面和其他账号资料的浏览器访问仍需核对。建立管理员建号、首次改密流程前，不将真实账号接入。
3. **正式数据保护：**明确独立数据卷、实际备份目录、每日自动备份、多版本保留、失败告警、密钥的独立保存与恢复方法；用正式配置的**虚构数据**再做一次 NAS 来源独立卷恢复。现有 NAS 演练只覆盖测试栈。
4. **运行与回退：**在独立预发布环境核对 `docker compose config --quiet`、Django `check --deploy`、迁移计划、登录页与 CSS/JS、账号隔离、DOCX 导出；记录代码与数据库版本。任何数据库变更前先配对备份数据库和私有原件，回退时二者与旧代码必须匹配。
5. **教师验收与批准：**真实资料使用授权、WPS 中公式和答案、实际打印、手机访问由用户实际核对。测试通过、备份与回退准备齐全后，仍须用户确认正式发布。

## 草案的离线核对方法

当前项目没有 `.env.production`，也没有在本机安装 Docker。可在本机用虚构值调用 `validate()` 测试闸门，不输入真实密码；运行结果只表示校验逻辑工作。将来在**Ubuntu 正式专用目录**配置私有 `.env.production` 时，先运行 `python3 scripts/check_production_env.py --env-file .env.production`，再执行 `docker compose --env-file .env.production -f compose.production.yaml config --quiet`。这两个命令会读取密钥，必须在用户获准的服务器操作窗口执行；不要把 `docker compose config` 的完整输出贴到聊天中。**目前这些 Ubuntu 命令均未执行。**

正式环境的准确目录、域名、HTTPS 转发方式、镜像固定版本和备份周期仍待现场确定。不要将测试栈改名或换端口充当正式栈，不将本草案直接 `up`。
