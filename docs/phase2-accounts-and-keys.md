## 已确认需求

- 第一版先供 2～5 位教师使用。管理员创建账号，成员首次登录修改密码；管理员可停用账号与重置密码，没有单独的“体验成员”类型。
- 每人的教学档案、对话、私人资料、作业和模型配置相互独立；资料默认私有，主动共享另行实现。管理页面只展示管理所需信息，不展示其他成员的私人文件、聊天内容或 API Key。
- 成员可以自行配置厂商、接口地址、Key 和模型；管理员可以为成员预配体验 API、额度及有效期。模型调用由教师主动触发，不自动购买、充值或静默转用付费接口。Plus 账号接入资格未确认，不作为本阶段实现依赖。
- 开发、预发布和正式环境分开。新版本在隔离环境通过测试并由用户确认后才正式发布；数据库变化前备份，代码回退与数据回退分别设计。

## 实施前代码核对（2026-10-17 本机静态检查；下列“当前没有”是当时状态）

- `workbench/models.py` 使用 Django 内置用户模型；教学档案、资料、作业、任务均有所有者，版本通过作业关联所有者。`workbench/views.py` 的当前资料下载、作业预览和 Word 导出按登录用户过滤；`workbench/tasks.py` 在开始处理时核对任务、作业、资料的所有者。
- `workbench/auth_views.py` 为普通与管理登录提供共用用户名维度限速。`config/admin_site.py` 使框架管理登录使用相同限速。`workbench/admin.py` 尚未注册私人业务模型。
- 当前**没有**管理成员账号的专用页面、强制首次改密、停用/重置工作流或成员密钥表。`config/settings.py` 的 `AI_PROVIDER`、`AI_BASE_URL`、`AI_MODEL`、`AI_API_KEY` 是进程级设置，不能当作多人独立配置。预发布站 AI 关闭且手动任务只针对经核对的虚构样例，不能直接扩展成成员自动调用。
- 当前项目目录不是 Git 仓库；此设计不建立远程仓库、不提交文件。上述代码核对只说明当前实现方式，不等于新功能已有测试证据。

## 实施顺序与验收

### 2A：账号生命周期（第一实施片）

1. 沿用 Django 内置用户表，不在已有迁移之后更换用户模型。新增一对一的账号状态，只保存“首次或重置后须改密”等非敏感标志。迁移现有账号时保留原账号和资料归属，不自动把已有测试账号停用或改密。
2. 管理员在专用成员管理页面创建普通账号，系统生成一次性临时密码，仅显示一次；由管理员通过双方约定的私下渠道交给成员，不写入日志、数据库明文字段、文档或聊天。用户名统一采用小写规则，避免大小写不同却共用登录限速计数的混淆。账号创建、停用、重置只允许持有明确“管理成员”权限者操作；不能仅凭 `is_staff` 判断，也不能停用最后一个可管理账号。
3. 成员用临时密码登录后，只能进入修改密码和退出入口；修改成功后才能访问工作台。成员改自己的密码需要校验旧密码；管理员重置生成新的临时密码并再次强制改密。停用与重置后，已登录的旧会话应在下一次请求失效；实现后用两个浏览器会话实测。
4. 管理页面只列用户名、启用状态、须改密状态和必要操作，不查询或展示私人资料、作业、聊天或密钥。管理操作记录操作者、目标账号、动作和时间，不记录密码或私人内容。保留框架后台供服务器维护，但不要向普通成员赋予后台权限；产品的管理员边界以专用页面及接口检查为准。

**本机与预发布验收：**用至少三个虚构账号（管理者、教师 A、教师 B）测试建号、首次改密、重置、停用、旧会话失效、非管理者拒绝访问管理入口、A/B 私有资料和 Word 互不可见；重置与停用不删除已有作业。先做自动测试，再在隔离预发布站用浏览器核对可见提示。不要使用真实教师账号或密码作为测试材料。

**2026-10-18 本机实施结果：**新增 `MemberAccess`、不含密码内容的 `MemberAudit`、专用成员管理页、首次/重置后强制改密、停用/重新启用与一次展示临时密码的页面；保留现有用户和资料归属。管理操作依赖显式 `manage_members` 权限，普通 `is_staff` 不自动获得；具有该权限的账号不列入普通成员操作目标，避免管理者自停用。首次改密时页面只呈现改密与退出入口；管理页只显示账号状态，不查询私人资料。6 项虚构账号专项测试通过；完整 `workbench` 回归 53 项通过，其中 3 项 PostgreSQL 专用测试按环境跳过；`manage.py check` 无问题，`makemigrations --check --dry-run` 无遗漏。**这些只是本机自动测试，尚未在预发布部署、浏览器操作或由用户实际验收。**测试暂未覆盖预发布 PostgreSQL 中的会话失效，也未单独覆盖所有 Word 下载权限组合。

### 2B：成员密钥保管（先用假 Key）

1. 每条模型配置绑定所有者；显示厂商、模型、状态，不回显完整 Key。成员只能新增、替换、删除自己的配置；管理员可为成员预配体验配置，但管理页面不能读取已存 Key。先只支持经逐个核对的接口模板；自定义地址在完成 HTTPS、重定向、内网地址和目标主机校验前不得携带 Key 发送请求。千问的现有单次虚构样例验证不自动推广到其他模型；DeepSeek 等厂商另测。
2. Key 入库前用经过认证的加密方式加密，随机生成每条记录的随机数，并绑定所有者和配置身份；数据库只保存密文、算法/密钥版本及必要元数据。加密主密钥放在数据库和代码仓库之外的受限服务器配置文件或等效密钥装载机制中，不与 Django 签名密钥混用。具体库和离线依赖包在实现前核对；**此处是设计要求，不表示已有加密代码**。
3. NAS 业务备份可包含密文数据库，但恢复还需独立保管的加密主密钥。分别验证：有正确主密钥时，隔离恢复的假 Key 可用；没有或错误主密钥时明确失败且不调用模型；换主密钥时旧记录可按版本迁移。主密钥本身的离线备份、访问人、轮换与丢失应对须单独定规程。数据库加密不能阻止掌握完整服务器权限者访问运行中的密钥。
4. 表单、异常、任务状态、日志、备份清单及管理页面不得泄露 Key。密码和 Key 不通过聊天传给助手。测试只用明显虚构的 Key，并在自动测试里断言普通成员和管理员页面均不回显密文或明文。

**本机与隔离恢复验收：**A 保存假 Key 后 B 无法读取、修改或使用；管理页面不能回显；数据库和日志不含假 Key 明文；备份恢复在正确主密钥下成功、错误主密钥下安全失败。此片完成前继续保持预发布站的真实自动 AI 调用关闭。
