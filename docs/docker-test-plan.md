**状态：Ubuntu 独立测试栈、PostgreSQL 虚构业务流程、回环页面资源及虚构数据的数据库/私有文件配对备份、OMV 专用 NFS 转存和 NAS 来源独立卷恢复均由用户现场输出验证。** 2026-10-16 首次构建因下载 Python 依赖超时，离线重试后四项服务显示运行，db/redis healthy，登录页 HTTP 200。原 35 项自动测试含 SQLite 专用场景，在 PostgreSQL 栈执行失败；独立 1 项虚构流程复核通过。第一次备份停在导出前并留下 `INCOMPLETE`，修订版成功输出 `TEST_BACKUP_FILES_VERIFIED`，目录 `backup-NX5wqA1m`；本机备份来源的新卷恢复输出 `INDEPENDENT_RESTORE_VERIFIED`，NAS 副本来源的新卷恢复输出 `NAS_SOURCE_INDEPENDENT_RESTORE_VERIFIED`。普通用户没有 Docker socket 权限，使用 `sudo`；本机没有 Docker 命令。

## 已确认的范围

- 只验证阶段 1 的上传、本人资料下载、草稿预览和 Word 导出等现有功能。Compose 测试栈强制关闭 AI，不能在此栈发送模型请求或验证费用。
- 测试栈名固定为 `teacher-workbench-test`，网页仅绑定测试主机的 `127.0.0.1:18000`。不得把该端口接入内网穿透、域名或公网；`runserver` 和 `DJANGO_DEBUG=1` 只用于隔离测试。
- 数据库、Redis 和私有上传文件各用独立 Docker 卷。既有 Windows 本机 SQLite 数据不会自动进入 PostgreSQL；不得把真实教学资料复制进测试卷。
- 最初的 Docker 测试栈阶段不建立正式环境、不挂载或写入 NAS、不修改 PVE，也不从用户的本地样本目录装入镜像。**后续授权变更：**用户于 2026-10-16 明确允许在 OMV 建工作台专用受限位置，并仅用虚构测试备份演练 NAS 转存与独立恢复；这不授权修改 PVE、现有共享或正式环境。专用 NAS 的虚构数据转存及独立恢复已按此授权演练，步骤见 [NAS 备份方案](nas-backup-plan.md)。

## 启动前核查（原定步骤；现场结果见下方当前闸门）

1. 确认 Ubuntu 的目标目录、磁盘余量、Docker Compose 可用、`18000` 端口占用，以及该目录与未来正式环境完全分开。用户此前提供的 `hello-world` 结果仅证明基础 Docker 当时可用。
2. 在**测试目录**从 `.env.example` 创建未入 Git 的 `.env`，分别生成至少 32 字符的 Django 密钥和至少 20 字符的数据库密码；保持 `AI_ENABLED=0`、`AI_API_KEY=`、`AI_LOCAL_QUEUE=0`。真实密钥不能写在本页、聊天或命令参数中。
3. 执行 `python3 scripts/check_test_env.py --env-file .env`。预期只输出“通过离线检查”，不显示任何密钥。该检查已在 Windows 用示例值、随机虚构值和误开启 AI 的配置测试；Ubuntu 用户随后反馈 `TEST_CONFIG_READY`。
   Web 和 worker 容器启动时还会用同一脚本检查进程环境，错误配置会阻止应用进程启动；这不能替代宿主机预检，因为数据库容器可能已用旧密码初始化卷。首次启动前必须先通过宿主机预检，避免之后误以为只改 `.env` 就能更改数据库内已有密码。
4. 再执行 `docker compose config --quiet`，核对 Compose 解析；随后检查 `docker compose config` 中的项目名、仅回环绑定的端口和三个数据卷。`config` 可能显示数据库密码，不能把完整输出贴到聊天或日志。
5. 只有上述通过且测试目录已明确，才考虑 `docker compose up -d --build`。首次启动会建立 PostgreSQL 数据卷并运行迁移，是服务器写操作；执行前应先说明路径和范围。启动后核对容器、登录页、静态资源、上传、权限与下载，不使用真实教学资料或付费模型。

## 数据备份边界

- **数据库卷**保存账号、资料元数据、任务和草稿版本；需要 PostgreSQL 一致性导出。单独复制容器卷文件不能替代一致性备份。
- **私有文件卷**保存上传原件；必须与数据库同一备份点对应。Word 导出目前从草稿动态生成，不应把重新下载的文件当成原件备份。
- **Redis 卷**是任务队列状态，不等同于成果版本。当前隔离栈关闭 AI，预期无付费任务；以后若运行 AI，恢复前须逐项核对任务是否已请求模型，避免重复调用和费用。
- 测试备份放在项目 Git 目录之外的受限位置，记下时间、应用代码版本、数据库导出、私有文件归档和校验值；密钥的安全恢复途径单独保存。专用 NAS 上已有一份虚构测试备份且恢复演练通过；正式业务数据备份、自动周期与保留策略尚未建立。

## 升级与回退顺序（待演练）

1. 停止网页与 worker 的写入，确认没有运行中的模型任务；记录当前镜像/代码版本及迁移版本。
2. 对 PostgreSQL 做一致性导出，并归档同一时点的私有文件卷；验证归档可读、校验值一致。只看到备份文件不算恢复成功。
3. 在**另一个隔离测试栈**用这两份备份和对应旧版代码演练恢复：检查登录、资料下载、历史版本、学生卷/教师版 Word，以及第二账号不可访问第一账号内容。此时不得覆盖现有测试卷。
4. 恢复演练通过后才能升级原测试栈并执行数据库迁移。若升级失败，先停写，再用迁移前数据库与私有文件**一起**恢复到匹配的旧版代码；单独回退代码不足以回退数据库结构或数据。
5. 正式环境以后另设独立配置、数据目录、可信 HTTPS、登录限速、静态资源服务和 NAS 多版本备份；测试栈不能直接公开或改名充当正式服务。
